    test(fr01): add 27 data-driven registration test cases

    Cover the password rule matrix, happy paths, required fields, e-mail
    format, duplicate e-mail, XSS and SQL injection payloads, the
    255-character name boundary, credential storage and UI/spec consistency.
    Six distinct assertion patterns are used and tagged P1 to P6 at each call
    site.

    Eight tests are tagged @bug and fail on purpose. They assert the behaviour 
    the specification and the on-screen hint promise, not the behaviour the
    code currently implements, and each red maps one-to-one onto a defect
    recorded in 23127195/bug-report/BUG_REPORT.md. Relaxing them to green
    would turn the defects into the specification.

    Three review fixes are folded in:

    - Account existence is proved by asking the back end how many user rows
    hold
     the address, not by asserting the URL is unchanged. The latter matches
     instantly, because right after the click the SPA has not resolved its
    POST
     yet, so four e-mail-format tests went green against a SUT that in fact
     accepts malformed addresses.
    - Required-field cases assert the HTML5 constraint validity state instead
    of
     the browser validation message, which differs across engines and locales.
    - API assertions wait for the SPA navigation first, otherwise they can
    outrun
     the registration request. That race surfaced only on WebKit.
